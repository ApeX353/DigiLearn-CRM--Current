## [LOW / CONFIRMED] verifyPassword's try/catch is dead code — an unparseable password hash turns login into a 500 instead of a 401 and skips lockout accounting

- file: `crm-v2-server/src/auth/auth.service.ts:692`
- new: true
- mechanism: ```
private async verifyPassword(hash, password): Promise<boolean> {
  try {
    return argon2.verify(hash, password);   // no await
  } catch (error) {
    return false;
  }
}
```
(auth.service.ts:688-697). `argon2.verify` returns a Promise; because it is returned rather than awaited, a rejection is adopted by the async function's own promise and never enters the `catch`. `@node-rs/argon2` rejects (it does not resolve false) when `hash` is not a valid PHC-encoded argon2 string. `login()` awaits `verifyPassword` at :209-212 outside any try/catch, so the rejection propagates out of the service as a non-HttpException and Nest maps it to 500. `handleFailedLogin` at :215 is never reached, so the attempt is not counted and `last_failed_login_ip` is not recorded. The same dead catch shields `changePassword`'s current-password check (:475-478).
- scenario: Any `account_security` row whose `password_hash` is not valid argon2 — a row imported from the previous system, a truncated/edited value, or an empty string (the column is `text NOT NULL` with no format constraint, migration 1700000000000-InitialSchema.ts:259) — makes `POST /auth/login` return `500 Internal Server Error` for that user on every attempt instead of `401 Invalid credentials`. The user sees a server error rather than a credentials error, the failure is invisible to the lockout counters, and the catch block gives maintainers false assurance that bad-hash cases degrade to 'wrong password'.
- verifier: auth.service.ts:688-697 is exactly as quoted: `return argon2.verify(hash, password);` inside try with no await, so a rejection is adopted by the outer promise and can never reach the catch — the catch is unreachable for async failures. Empirically checked the actual installed dependency (@node-rs/argon2 2.0.2, auth.service.ts:12): `verify('not-a-hash','x')` and `verify('','x')` both REJECT with 'Invalid hashed password: password hash string missing field' — they do not resolve false. login() awaits verifyPassword at :209-212 with no surrounding try/catch and there is no ExceptionFilter anywhere in src/ (grep for ExceptionFilter/useGlobalFilters returned nothing), so the rejection surfaces as a non-HttpException -> Nest default 500, and handleFailedLogin at :215 is skipped. changePassword's current-password check at :475-478 shares the same dead catch. Low is correct: requires an already-corrupt password_hash row, no privilege gain.

## [LOW / CONFIRMED] 2FA can be stripped with only a code — no password re-authentication, no throttle, and TOTP codes are replayable for ~90 seconds

- file: `crm-v2-server/src/auth/two-factor.service.ts:147`
- new: true
- mechanism: `disable2FA(userId, code)` requires nothing but a valid access token plus `verify2FA` (two-factor.service.ts:133-151); it never asks for the account password, and on success it wipes `two_factor_secret` and all backup codes (:154-158). The route `POST /auth/2fa/disable` carries only `@SkipRolesCheck()` with no `@Throttle` (auth.controller.ts:501-532) — unlike `/auth/login` (10/min), `/auth/password/request-reset` (5/min) and `/auth/password/reset` (10/min) — so only the 300/min global limit applies, and the report's §9.5 shows even that is keyed on an attacker-supplied header. `verify2FACode` uses `totp.validate({ token, window: 1 })` (:219) and nothing records the last accepted counter (`account_security` has no such column, entity lines 36-44), so a given 6-digit code stays valid for three 30-second steps and can be replayed any number of times inside that window. `regenerate-backup-codes` (:535) and `2fa/generate` (:423) are likewise password-free and unthrottled.
- scenario: An attacker holding a stolen or borrowed access token (7-day lifetime per §9.1) posts one observed 6-digit code — shoulder-surfed, phished, or replayed from a code the victim just used up to 90 seconds earlier — to `POST /auth/2fa/disable`. The victim's second factor is permanently removed and their backup codes deleted, without the attacker ever knowing the password, and with no per-account attempt counter to notice the guessing (§9.6 already established that 2FA failures never increment lockout). The victim gets no notification: nothing in the disable path calls NotificationsService.
- verifier: two-factor.service.ts:133-158 matches: disable2FA(userId, code) looks up account_security, calls verify2FA, and on success sets two_factor_enabled=false, two_factor_secret='' and two_factor_backup_codes=[] — no password argument anywhere in the signature or body, and no NotificationsService call. Route decorators confirmed by grep on auth.controller.ts: 2fa/disable at :501-502 carries only @SkipRolesCheck() with no @Throttle, as do 2fa/generate (:422-423) and 2fa/regenerate-backup-codes (:534-535), while login (:117), password/request-reset (:287) and password/reset (:320) all carry explicit @Throttle. verify2FACode at :209-225 uses totp.validate({ token, window: 1 }) and the account_security entity has only two_factor_enabled/_secret/_backup_codes (lines 37-43) — no last-accepted-counter column, so a code is accepted across three 30s steps and replayable within it. Low is the right severity: the attack still presupposes a stolen access token plus an observed code, so it is a defense-in-depth gap (missing step-up auth) rather than a standalone bypass.

## [LOW / UNVERIFIED] The R1 soft-delete guard in listProposals is dead code — .where() at :298 discards the .andWhere() at :294

- file: `crm-v2-server/src/automation/services/lead-auto-router.service.ts:294`
- new: true
- CHALLENGES EXISTING REPORT: Partially challenges §11.2, which cites lead-auto-router.service.ts:283-301 and treats the query as correct-but-unpaginated; the pagination claim is confirmed, but the R1 deleted_at guard those same lines advertise is not actually in the emitted SQL.
- mechanism: `listProposals` chains `.andWhere('lead.deleted_at IS NULL')` at `lead-auto-router.service.ts:294` and then `.where('p.status = :status', { status })` at `:298`. TypeORM's `SelectQueryBuilder.where()` replaces the accumulated WHERE expression rather than appending to it (that is the documented difference between `where` and `andWhere`), so the explicitly-authored guard on line 294 — the one the R1 comment at `:286-290` says exists to stop orphaned proposals rendering as bare IDs — never reaches the generated SQL. Related and confirmed: the method is genuinely unpaginated — the chain ends in `.getMany()` at `:300` with four eager joins and no `take`, matching §11.2's 447 KB measurement.
- scenario: Add `withDeleted()` (or refactor the innerJoin) to `listProposals` for any reason — the soft-deleted-lead filter silently disappears, because line 294 was never contributing to the query, and the approval queue regresses to showing 'record unavailable' bare-ID rows exactly as described in §5.4.
